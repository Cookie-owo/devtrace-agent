## 上下文

后端目前在 `/health` 混合了活性检测与 Milvus 可用性，将依赖 readiness 暴露为 `/readiness`，并且没有区分无效跟踪配置与外部服务不可用的端点。前端仅需要用于工作区标题的轻量级活性检测。

## Goals / Non-Goals

**目标：**
- 提供稳定、独立的存活状态 (`/health`)、readiness (`/ready`) 和配置诊断 (`/config/check`) APIs。
- 并发探测 SQLite、Milvus、Qwen 和 MCP 以进行 readiness，同时在探测抛出异常时保留单独的安全结果。
- 将提供者密钥、CLS 凭据、请求授权和任意异常细节排除在所有诊断响应之外。
- 仅让前端工作区连接依赖于存活状态。

**非目标:**
- 添加指标后端、使诊断认证或更改依赖项启动顺序。
- 在模块导入时重新连接或替换现有的提供者抽象。

## 决策

### 三个有意分开的端点语义
`/health` 仅返回服务元数据，不执行任何依赖工作。`/ready` 报告进程是否可以提供完整的产品依赖集，并在任何必需的依赖不可用时返回 503。`/config/check` 首先验证跟踪的配置部分，然后包含相同的安全运行状况探测结果，使无效配置与临时连接故障区分开来。

这避免了将存活状态作为编排的门禁。考虑过重用`/readiness`，但`/ready` 是请求的稳定合约，而兼容别名将保留模糊的旧版API。

### 在 API 边界处的安全探测适配器
应用程序存储其异步 SQLAlchemy 会话工厂，并为 SQLite 执行 `SELECT 1`。Milvus、LLM 和 MCP 保留其现有的 health/readiness 方法。每个方法都由一个窄型探测适配器封装，该适配器会捕获配置和连接异常，报告通用的安全错误类别，并允许同级检查完成。

### 配置验证是结构化的且已脱敏
`/config/check` 加载所需的后端、向量、LLM 和 MCP 配置边界，而不会序列化其原始映射。它返回部分有效性以及安全标识符，例如模型、基础 URL、向量 URI 和 MCP 端点。任何包含秘密的字段都不会被复制到响应或日志器中。

## Risks / Trade-offs

- [A Qwen readiness 请求会消耗提供者容量] -> 仅在 `/ready` 和 `/config/check` 上使用现有的最小提供者 readiness 调用，绝不在 `/health` 上使用。
- [一个慢速依赖延迟了 readiness] -> 并发运行独立探测，并遵守每个提供者配置的超时时间。
- [诊断输出意外暴露了一个密钥] -> 使用类型安全的有效负载，并在测试中断言敏感信息被删除。
- [现有客户端调用 `/readiness`] -> 在共享契约中发布 `/ready`；这个从零到一的项目不会保留过时的路由。

## 迁移计划

1. 为隔离的存活状态、聚合 readiness 和安全配置诊断添加失败的端点/契约测试。
2. 实现探测适配器并替换过时的 readiness 路由。
3. 重启本地后端，验证 healthy/降级路径，然后同步、归档、提交并推送。
