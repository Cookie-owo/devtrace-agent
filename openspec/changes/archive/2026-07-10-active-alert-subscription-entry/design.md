## 上下文

已认证的 AIOps 工作流已持久化诊断任务并接受一个可选的结构化警报对象。其手动 JSON 输入字段适用于临时调查，但不会为操作员提供当前警报的视图，也不会自动保留原始外部警报有效负载。该项目使用已提交的 JSON 配置文件，并有意不读取机器环境变量以进行项目配置。

## Goals / Non-Goals

**目标：**
- 在模块导入期间不连接的情况下查询配置的 real Alertmanager 兼容的警报 API。
- 对操作员需要进行分类的字段进行标准化，同时保留原始警报负载以用于诊断执行。
- 在已认证的 AIOps 工作区中明确显示警报列表及其失败情况。
- 通过现有的类型化创建并 SSE 路径启动诊断，保留所选的警报上下文。

**非目标：**
- 接收 webhook，修改 Alertmanager 静默，确认警报，或托管一个警报系统。
- 添加演示警报、仅限浏览器的替代方案，或特定于供应商的 SDK。

## 决策

### Alertmanager 兼容的 HTTP 提供商
创建一个显式的后端提供商，该提供商从跟踪的 `prometheusAlerts` 配置部分中读取 `alertsApi` URL 和超时时间。当调用 API 时仅使用 `httpx.AsyncClient`，并调用 `GET /api/v2/alerts`（配置值是完整的端点 URL）。该提供商验证响应结构，仅返回状态为活动的警报，并对传输、HTTP、JSON 或结构失败情况引发安全的提供商错误。

### 标准化显示加上原始上下文
API 返回一个包含告警名称、服务、严重性、状态、开始时间、摘要、标签、注释和原始外部负载的 `ActiveAlert` 对象。客户端列出标准化字段，但将原始负载加上标准化标识符传递到现有的 `CreateAiopsDiagnosticRequest.alert` 字段中。这避免了有损的重建，并让 Planner 获得实际的告警上下文。

### 已认证的获取和显式失败状态
"`GET /aiops/alerts/active`" 需要当前的 "user"，尽管警报是从配置的外部服务读取的，而不是作为共享的 "tenant" 数据存储。前端会与 "AIOps" 历史记录一起加载它，提供手动刷新控制，并在标准化的提供者错误上呈现简洁的失败状态。它永远不会将过时或虚构的警报作为当前警报显示。

### 重用诊断流路径
选择警报会从其标准化字段中得出明确的事件问题，并使用现有的 AIOps Pinia 存储来创建和流式传输诊断。不引入单独的任务创建 API 或客户端计划。

## Risks / Trade-offs

- [外部服务不可用] -> 返回 `SERVICE_UNAVAILABLE` 并附带安全消息，公开重试操作；不要伪造警报数据。
- [Alertmanager 负载变体] -> 对已知的 `v2` 字段进行防御性验证，并将可选的标签/注释保留为字符串映射。
- [大量警报列表会占据工作区] -> 使用有界、可滚动的操作列表，不干扰诊断表单或历史记录。
- [选定的警报在执行前发生上游变化] -> 诊断存储创建时发送的警报负载，保留被调查的上下文。

## 迁移计划

1. 添加完整的 real-alert 端点配置和提供者边界。
2. 添加经过身份验证的 API 和共享合约，然后通过测试覆盖成功和不可用提供者的行为。
3. 添加 AIOps 警报列表和选择流程，然后针对配置的端点执行真实的本地请求。
4. 回滚会移除端点和 UI 面板；持久化的 AIOps 任务仍然有效，因为它们已经存储了警报输入负载。
