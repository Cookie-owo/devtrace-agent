## 上下文

现有的已认证警报端点读取一个 Alertmanager v2 端点，而提供的外部测试服务在 `/api/v1/alerts` 暴露 Prometheus v1 警报，并且目前返回空的实时结果。CLS 种子使用安全但通用的合成场景。AIOps 图表已经消耗了一个警报负载，在执行有限的 `SearchLog` 之前检索知识，并且持久化其证据链。

此更改必须提供一个可复现的真实集成演示，而不会使 fixtures 成为启动的副作用。仓库配置是唯一的配置源，提供者凭据有意为此私有开发仓库进行跟踪。

## Goals / Non-Goals

**目标：**

- 作为唯一的附加 Docker 服务运行本地 Alertmanager，并将其 v2 API 发布一个真实的活动警报。
- 将配置的 Prometheus v1 和 Alertmanager v2 读取源聚合到现有的已认证警报端点中。
- 生成结构化的 Java 电商量化服务 CLS 日志和匹配的 SOP 文档，然后使用真实的 MCP 和 CLS 路径执行由警报驱动的诊断。
- 使设置和可重复演示命令成为显式的脚本，绝不能作为应用程序启动行为。

**非目标：**

- 不要部署 Prometheus、通知接收器或完整的监控堆栈。
- 不要在运行时代码中伪造提供者响应，将警报测试数据存储在 SQLite 中，或更改 tenant owner 传输规则。
- 不要配置生产环境基础设施，或超出其有限真实工具设计的 AIOps 计划器。

## 决策

### 一个提供者背后的多个类型警报源

活动警报提供者将为每个 `prometheusAlerts.sources` 条目构建一个类型化读取器，并聚合成功的响应。Alertmanager v2 读取器解析数组响应；Prometheus v1 读取器解析 `data.alerts`。每个标准化警报在其上下文中包含源标识符，因此所选警报在整个诊断过程中保留来源信息。这取代了单一的 `alertsApi` 配置。

将外部服务视为Alertmanager的替代方案被拒绝，因为其Alertmanager v2路由返回404，而其Prometheus v1警报路由返回了文档中记录的成功封装。仅使用本地服务的替代方案被拒绝，因为它会导致提供的外部源未被测试。

### 真实的部分源代码行为

聚合端点会返回来自成功源的警报，并且仅当每个配置的源都失败时才会失败。单个源的失败消息保留在服务器日志中，而不是 API 有效负载中，因此不会暴露凭据和提供者内部信息。有效的空结果仍为空结果，永远不会被替换为警报。

### 明确的确定性演示固定装置

CLS 脚本将创建安全的结构化日志字段，看起来像 Java 量化定价服务事件：请求/跟踪 ID、服务和环境标签、订单/工具标识符、重试和恢复事件、延迟以及有限的错误描述。一个单独的发布者会发布一个匹配的 Alertmanager 警报。一个单独的本地演示脚本会注册或登录专用配置的演示账户，通过真实的后端 API 上传并索引 SOP，并且只能在本地后端被故意启动后运行。

在应用启动时自动填充测试用例的替代方案被拒绝，因为它会隐藏有状态的外部副作用，并违反现有的显式上传产品行为。

### Docker 边界

`infra/compose.yaml` 通过跟踪的最小接收器配置、持久化数据卷和主机端口 9093 获得 `alertmanager`。本地后端、前端和 MCP 服务器保留其现有的直接启动工作流。fixture 发布器通过主机端口与 Alertmanager 通信，而不是通过 Docker shell 命令。

## Risks / Trade-offs

- [外部 Prometheus 当前没有活动警报] -> 保留真实的空响应，并仅使用本地 Alertmanager 源来演示活动警报。
- [CLS 数据摄入可能需要时间] -> 演示文档指出短时的数据摄入延迟，诊断搜索窗口覆盖最新一天。
- [失败的源可能会掩盖其他正常的 health 源] -> 聚合成功的读取，并且仅在没有源成功时显示不可用。
- [重复发布会导致重复警报] -> 使用稳定的标签和指纹维度，并为清理提供明确的解决命令。
- [测试账户和数据在本地持久化] -> 使用明确命名的演示账户和正常的 owner 范围存储；脚本为可选。

## 迁移计划

1. 添加 Alertmanager 服务并使用 `docker compose -f infra/compose.yaml up -d alertmanager` 显式启动它。
2. 用类型化的源条目替换单个警报配置，保留 `config/project.json` 中的所有 URL 和凭据。
3. 部署聚合提供者、脚本、SOP fixture 和测试。
4. 发布日志和本地警报，上传/索引 SOP，然后调用由警报驱动的诊断并检查其持久化的证据链。
5. 通过删除新的源配置和 Alertmanager 服务进行回滚；不需要数据库迁移或破坏性数据操作。

## 开放问题

无。提供的外部服务为只读，返回真实的空警报列表；本地 Alertmanager fixture 提供了端到端演示所需的活动信号。
