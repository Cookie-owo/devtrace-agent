## 上下文

后端已共享 API 合同和 SQLite 内存层，但尚未有 HTTP 应用或 user 边界。一旦添加真实的 user 工作流，聊天、知识库和 AIOps 数据必须不再匿名。

此更改引入了第一个 HTTP 应用程序表面，并使用现有的内存数据库/migration 模式用于 user 和身份验证会话。它还将前端从基础状态页面升级为一个小型已认证的应用程序外壳。

## Goals / Non-Goals

**目标：**

- 提供注册、登录、注销和当前-user API 端点。
- 仅存储密码哈希，通过 `pwdlib` 使用 Argon2。
- 会话使用不透明的承载令牌；仅持久化令牌哈希，因此数据库读取无法恢复承载令牌。
- 所有认证成功和失败的响应都使用现有的统一响应封装。
- 使用相同的 current-user 依赖项保护知识库、聊天和 AIOps API 入口点。
- 添加前端登录/register/logout流程并在重新加载时保持认证状态。

**非目标：**

- 基于角色的访问控制、组织成员身份、密码重置、电子邮件验证、MFA、社交登录或刷新令牌轮换。
- 超过受保护占位符路由的完整 chat/knowledge/AIOps 实现，用于身份验证门控。
- Cookie/CSRF 加固；此流程首先从前端客户端使用授权 bearer 头。

## 决策

### 决定：FastAPI 基于依赖的授权守卫应用

在 `super_ai.api` 下添加一个带有认证端点和受保护占位路由的小型 FastAPI 应用。FastAPI 依赖项将把 bearer 令牌解析为当前的 user，受保护的路由将使用该依赖项。

考虑过的替代方案：
- 仅构建服务端认证，不包含 HTTP 路由：更简单，但无法满足前端/API 的访问需求。
- 添加更重的框架堆栈：对于此基础来说不必要，且与轻量级后端不一致。

### 决策：使用不透明会话令牌而非 JWT

在登录/注册时，生成一个高熵令牌，仅返回一次，仅将 SHA-256 令牌哈希与会话元数据一起存储，并在注销时撤销它。这提供了立即注销语义并保持令牌验证简单。

考虑过的替代方案：
- JWT 访问令牌：通用且无状态，但注销/撤销需要额外的基础设施，此应用已具备 SQLite。
- 服务器端 Cookie：以后很有用，但对当前 Vite 客户端和 API 测试来说，持有者头更简单。

### 决策：使用 `pwdlib[argon2]` 进行密码哈希处理

使用 `PasswordHash.recommended()` 进行密码哈希和验证，并将所有哈希操作隐藏在认证服务之后。测试断言明文密码永远不会出现在数据库行或 API 响应中。

考虑过的替代方案：
- 手动编写的 PBKDF2 使用标准库：依赖项更少，但更容易配置错误且不够未来友好。
- bcrypt/passlib：可行，但 FastAPI 当前的安全示例使用 `pwdlib` 与 Argon2。

### 决定：共享合同拥有授权 DTOs 和错误

`packages/api-contracts` 将导出身份验证请求/响应类型，添加身份验证 OpenAPI 路径，并添加 `AUTH_INVALID_CREDENTIALS`、`AUTH_UNAUOpenAPITICATED` 和 `AUTH_SESSION_REVOKED` 错误代码。后端和前端测试将与这些结构保持一致。

考虑过的替代方案：
- 仅后端本地 DTO：更快，但违反了现有的单一来源合同规则。

## Risks / Trade-offs

- 本地存储中的 Bearer 令牌可能通过 XSS 暴露 -> 保持 UI 简单，避免不安全的 HTML，并将强化的 cookie/会话策略留到后续的安全更改。
- SQLite 会话写入足够用于本地/单进程使用，但不是分布式生产认证存储 -> 仓库边界允许替换。
- 占位符受保护路由尚未实现业务数据 -> 测试仅断言认证网关和统一错误，而非未来数据行为。
- 密码策略有意保持最小 -> 要求非空的电子邮件/显示名称和密码长度，将更强的策略留到后续产品决策。

## 迁移计划

1. 添加身份验证依赖项，并为 `users` 和 `auth_sessions` 添加第二个 Alembic 版本。
2. 通过内存边界添加身份验证 SQLAlchemy 模型和仓库操作。
3. 添加密码哈希处理、令牌生成/哈希处理以及身份验证服务操作。
4. 添加 FastAPI 应用、统一的响应帮助程序、身份验证路由、当前-user 依赖项和受保护的占位符路由。
5. 添加共享合约和前端身份验证客户端/UI.
6. 运行迁移和所有后端/frontend/contract/OpenSpec 检查。

回滚通过 Alembic 降级删除新的身份验证表，并移除身份验证服务 /API/frontend UI。现有的内存表保持不变。

## 开放问题

此变更没有未决问题。未来的安全工作应决定 cookie 与 bearer 的部署策略、密码重置和角色/tenant 授权。
