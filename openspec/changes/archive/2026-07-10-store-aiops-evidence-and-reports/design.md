## 上下文

诊断工作流已存储一个 owner 范围的任务、工具调用审计、LangGraph checkpoint，以及最终报告。其计划和证据目前嵌入在 JSON 数据包中，因此调用者无法列出单独的证据项、区分证据类型，或在不解码特定于实现的数据包的情况下证明报告使用了哪些证据。

## Goals / Non-Goals

**目标：**

- 将诊断计划和执行阶段作为有序的、tenant范围内的步骤记录进行存储。
- 为日志、指标、警报、工单和知识引用存储类型化的证据记录，并包含其原始负载和源元数据。
- 持久化报告到证据的链接，并提供经过身份验证的完整证据链查询。
- 保留现有的任务、审计、checkpoint和报告行为，同时使历史诊断在当前owner作用域内可查询。

**非目标：**

- 在此次变更中引入新的指标、工单或警报提供者。
- 重新编写现有的历史任务 JSON 数据载荷为标准化行。
- 添加一个 AIOps 前端仪表板；API 和共享合约提供后端边界。

## 决策

### 使用规范化的步骤、证据和报告链接表

`aiops_diagnostic_steps` 存储有序的 Planner、Executor、Replanner 和 Report 记录。`aiops_diagnostic_evidence` 存储不可变的证据，包括类型、源引用、摘要、原始 JSON 有效负载、可选步骤 ID 和可选工具调用 ID。`aiops_report_evidence_links` 将报告与它使用过的每条证据记录相关联。仅用于 JSON 的存储被拒绝，因为它会使高效的历史记录、类型过滤、访问控制和溯源查询变得脆弱。

### 所有新行和每个查询都包含所有者范围

所有记录都包含 `owner_user_id`，并以外键方式关联到其任务，并使用 owner/task 索引。存储库方法首先接受 `owner_user_id`，并在写入前验证父 owner 关系。这遵循现有的内存存储库模式，并允许以后的 PostgreSQL 实现而无需业务层 SQL 更改。

### 在生成节点上保留证据

工作流在图执行前存储警报输入，SOP 在 Planner 中的检索命中，以及 Executor 中的工具结果。它在每个图节点处存储步骤记录，并在从图状态收集证据 ID 后在 Report 中写入报告链接。检查点对于图恢复仍然有用，但可查询的证据链不再依赖它们。

### 提供单独的历史记录和证据链 APIs

`GET /aiops/diagnostics` 以最新优先的顺序列出当前 user 的历史任务，并具有可选的包含时间范围。`GET /aiops/diagnostics/{id}/evidence-chain` 返回任务、有序步骤、通用工具审计、证据记录、checkpoint、报告以及每个报告的关联证据 ID。由于单个过大的任务负载无法独立查询或安全地演进，因此被拒绝。

## Risks / Trade-offs

- [证据有效负载可能很大] → JSON 必须忠实存储，但在面向列表的响应中使用有限的摘要，并保留当前 MCP 输出边界。
- [报告可能在后期证据项之前编写] → Report 仅在图执行证据最终确定后才持久化链接；测试断言每个报告链接在同一任务和 owner 范围内解析。
- [现有的本地 SQLite 数据库需要模式更改] → 添加一个 Alembic 迁移，包含可逆的外键和索引；本地启动在验证前升级到最新版本。
- [未来的证据提供者具有不同的模式] → 使用稳定的 kind/source/payload 封装，而不是提供者特定的列。

## 迁移计划

1. 添加 SQLAlchemy 模型和用于步骤、证据和报告链接的 Alembic 迁移。
2. 扩展仓库协议和 SQLite 实现，然后更新 LangGraph 诊断服务，在生成证据时将其写入。
3. 添加合约和经过身份验证的 API，运行迁移，启动本地后端/前端/MCP 进程，并执行真实的 CLS 诊断以查询其持久化的证据链。
4. 通过降级迁移并还原应用更改来回滚；现有的任务、报告、审计和 checkpoint 表不受影响。

## 待解决问题

- 无。新的指标、工单和警报集成在添加其真实工具时将重用类型化的证据信封。
