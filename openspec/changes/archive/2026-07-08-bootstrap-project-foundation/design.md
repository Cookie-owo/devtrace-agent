## 上下文

仓库当前包含 OpenSpec 工作流文件和仓库指南，但没有应用程序模板。此更改建立了未来提案的第一个实现基础：一个包含 Python 后端、Vue 前端、共享 API 合同、基础设施占位符、文档以及可重复的验证命令的单体仓库。

仓库指南已定义了预期的堆栈：后端代码位于 `apps/backend/src/super_ai`，FastAPI/Pydantic 导向的 Python 约定，`uv` 作为 Python 工作流，Vue 3/Vite/TypeScript 用于前端，以及以 OpenSpec 优先的功能交付。

## Goals / Non-Goals

**目标：**
- 创建每个区域所需的请求的 monorepo 目录和最小文件，以使其可被发现。
- 通过 `super_ai` 使用 `src` 布局使后端包导入工作。
- 通过 `apps/backend/pyproject.toml` 配置后端质量工具。
- 提供一个 Vue 3，Vite，TypeScript 前端脚手架，包含测试和构建脚本。
- 在 `packages/api-contracts` 下提供一个类型化的共享合约包。
- 使用仅占位符的环境示例记录开发和验证工作流程。

**非目标：**
- 不包含身份验证、聊天、知识库、AIOps、Milvus、MCP 或 LLM 运行时行为。
- 不包含生产 Docker 镜像加固或部署环境配置。
- 不包含任何历史目录结构的兼容性适配器。
- 不包含真实密钥、外部服务凭据或供应商特定的运行时连接。

## 决策

### 决策：将后端和前端工具链保留在每个应用本地
后端拥有 `apps/backend/pyproject.toml` 并从 `apps/backend` 使用 `uv` 运行。前端拥有 `apps/frontend/package.json` 并从 `apps/frontend` 使用 `npm` 运行。

考虑过的替代方案：
- 根级别 Python 元数据：被拒绝，因为 Python 打包应保持在后端包的范围内。
- 单一根任务运行器：因在多个可运行服务存在之前添加了协调机制而被基础架构拒绝。

### 决策：使用一个小的可导入后端应用包
后端从 `super_ai` 包元数据和一个极小的 health 有效负载函数开始。测试验证导入行为，并为将来安全地附加 FastAPI 应用程序接线提供一个位置。

考虑过的替代方案：
- 立即添加一个 FastAPI 应用程序：被拒绝，因为请求是针对项目基础，而不是 API 行为。
- 保持 `src/super_ai` 空白：因为这无法证明包导入或工具配置。

### 决定：使用 Vue 3 加 Vitest 进行前端验证
前端使用 Vite、Vue 3、TypeScript、`vue-tsc` 和 Vitest。一个最小的组件和单元测试证明了模板可以进行类型检查、测试和构建。

考虑的替代方案：
- 不使用前端测试运行器：被拒绝，因为请求明确要求一个前端测试目录。
- 浏览器端到端测试：由于仅是基础更改，被认定为过早。

### 决定：将 `packages/api-contracts` 设为 TypeScript 包
共享的合约包通过 `src/index.ts` 暴露类型化的 API 合约定义。前端通过 npm 工作区依赖项使用它。

考虑的其他方案：
- 仅 JSON 模式：被拒绝，因为即时前端堆栈是 TypeScript，并且从直接类型化导入中受益。
- 后端生成的合约：被拒绝，因为后端 API 行为尚不存在。

### 决策：为基础设施和文档使用占位符
`infra` 和 `docs` 目录接收小而有针对性的文件，以确保结构稳定，而不暗示生产环境的 readiness。

考虑过的替代方案：
- 完整的 Docker Compose 堆栈：被拒绝，因为目前还没有实际的服务或依赖项需要协调。
- 仅空目录：被拒绝，因为空目录不会被 Git 跟踪。

## Risks / Trade-offs

- `npm install` 和 `uv sync` 依赖开发环境中的包可用性 → 缓解措施：保持依赖主流，并且仅固定广泛兼容的版本范围。
- contracts 包是 TypeScript-first，而后端是 Python → 缓解措施：将其视为前端可见的合约源，直到后续提案引入 API 生成。
- 最小脚手架可能被误认为是产品行为 → 缓解措施：README 和文档明确说明这仅为基础功能。
- 分支创建可能因 Codex 沙箱写入限制而受阻 → 缓解措施：将所有实现更改保留在工作树中，并明确报告分支限制。

## 迁移计划

1. 为基础功能添加 OpenSpec 工件。
2. 添加单仓库目录、包元数据、测试脚手架、README、环境示例和占位符。
3. 运行 OpenSpec 验证以及后端和前端验证命令。
4. 将新的 `project-foundation` 规范同步到 `openspec/specs` 中。
5. 归档已完成的变更。

在特性工作建立在此基础之前，回滚操作是直接的：删除添加的目录和归档的更改，然后恢复之前的 OpenSpec 规范集。

## 开放问题

此基础更改无相关内容。后续提案应决定具体的后端 API 框架连接、运行时基础设施、认证和生成的合约策略。
