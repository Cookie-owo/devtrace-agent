## 上下文

报告节点已经具有完成的诊断任务、最终报告和持久性证据标识符。现有的手动端点按需构建 Markdown 知识文档，但没有结构化的案件记录，不会自动运行，也没有专用的浏览路径。

## Goals / Non-Goals

**目标：**
- 在任务 owner 的范围内，每个成功的任务都精确地持久化一个结构化的案例。
- 从案例到其诊断任务、报告、证据、生成的文档和索引任务保持可追溯性。
- 重用已建立的文档/index-task管道，使案例成为tenant-过滤的检索源。
- 仅显示当前 user 的用例，并保留失败的诊断任务而不创建用例。

**非目标：**
- 重写历史手动用例文档，推断不支持的根本原因，或为失败/取消的诊断创建用例。

## 决策

### 专用的诊断案例表和存储库边界
添加 `aiops_diagnostic_cases`，并具有唯一的 owner/task 关系以及结构化的标量/JSON 字段。存储库方法仅通过任务创建、读取和列出案例，并且需要一个 owner id。生成的知识文档 id 和报告/证据引用存储在案例中，这样 UI 和检索可以追溯来源而无需解析 Markdown。

### Report-node 持久化钩子
在 AIOps 诊断服务中注入一个狭窄的用例持久化边界。在报告被持久化并将任务状态更新为 `succeeded` 后，它从真实任务输入、报告有效负载/内容和关联证据中提取字段，创建结构化的用例，创建知识文档和标准索引任务，然后异步安排索引。如果失败，报告节点不会调用它。

### 保守的结构化字段推导
当存在时，警报名称/服务从提供的警报字段中获取；关键词为规范化查询术语；根本原因和纠正措施仅从显式的报告有效载荷字段或限定的报告部分推导得出，当没有可靠来源时使用空字符串。完整的有证据支持的报告仍然是权威叙述，并带有结构化元数据进行索引。

### 案例库重用 AIOps owner 船舶控制
在现有身份验证下公开 `GET /aiops/diagnostic-cases`。AIOps 工作区会将其与历史记录一起加载，渲染简洁的案例行，并通过现有的 owner 作用域路由打开关联的证据链/文档。不会在浏览器 localStorage 中存储任何案例。

## Risks / Trade-offs

- [索引在案例持久化后失败] -> 保留结构化的案例和正常的文档/索引失败状态，以便操作员可以检查并重试标准的索引任务。
- [Report 缺乏明确的根本原因/修复方法] -> 存储空的结构化字段，并显示基于证据的报告，而不是捏造结论。
- [重复的报告完成] -> 强制执行唯一的 owner/task 案例记录，并从持久化器中返回现有记录。
- [案例字段暴露跨tenant的数据] -> 每个仓库读写和 API 列表都限定于 owner ID；生成的向量保留 owner/tenant 元数据。

## 迁移计划

1. 添加 schema/migration/repository 和持久化测试。
2. 连接自动成功报告持久化、文档索引和案件列表 API。
3. 添加 AIOps 案件库，验证真实的成功诊断会创建一个已索引的案件，然后进行归档。回滚不会删除现有案件，但会禁用未来的持久化。
