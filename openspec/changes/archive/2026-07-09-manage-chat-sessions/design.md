## 上下文

后端已经具有经过身份验证的 user，用于 `chat_sessions` 和 `chat_messages` 的 SQLite 内存模型，以及创建会话和追加/列出消息的仓库方法。公开的 API 仅暴露会话创建和单个会话查找，而前端显示静态聊天占位符。这意味着 SQLite 还不是面向 user 的聊天工作流的操作性真相来源。

聊天数据必须与知识文档、检索和AIOps数据使用相同的tenant边界：经过身份验证的user ID是当前tenant作用域。实现必须将业务和API代码隐藏在仓库接口之后，以便以后可以用PostgreSQL或其他存储替换SQLite。

## Goals / Non-Goals

**目标：**
- 向已验证的 API 暴露创建、列出、读取、清除和删除聊天会话的功能。
- 通过基于 SQLite 的存储库持久化 user 和助手消息，并从后端 API 返回完整的会话历史记录。
- 从显式输入或第一个保存的 user 消息生成初始会话标题。
- 保留消息元数据以用于知识引用和工具调用关联。
- 添加所有聊天会话管理操作的共享 TypeScript 合同和 OpenAPI 路径。
- 添加前端客户端/状态/UI 支持，从后端加载聊天数据并在注销时清除它。

**非目标：**
- 在此次更改中实现实际的 LLM 聊天流或代理编排。
- 实现多 user 组织 tenant 模型；已认证的 user ID 仍保持为 tenant 范围。
- 将聊天会话存储在浏览器 localStorage 中作为主要数据源。
- 添加分页功能，超出由仓库边界已覆盖的时间和更新顺序。

## 决策

1. 对所有聊天的读写操作使用现有的内存仓库边界。
   - 理由：`SQLiteChatMemoryRepository` 已经负责会话/消息的持久化和 tenant 过滤，因此通过 `update_title`、`clear_messages` 和 `delete_session` 扩展它，可以保持 API 代码独立于 SQLAlchemy 的细节。
   - 考虑的替代方案：在API路由中直接使用SQLAlchemy。被拒绝，因为这会违反仓库抽象，使替换PostgreSQL更困难。

2. 保持聊天消息元数据 JSON 格式，并将其作为 `metadata` 进行规范化，引用/工具引用应位于稳定的键中。
   - 理由：当前的 `ChatMessageModel.metadata_json` 已经保留了结构化的有效载荷。一个稳定的契约现在可以支持 `citations` 和 `toolCallIds`，而无需在代理运行时存在之前引入单独的表。
   - 考虑过的替代方案：现在创建专用的引用/工具关联表。由于目前还没有聊天流式传输运行时写入这些标准化关系，因此被判定为过早。

3. 从请求数据同步生成标题。
   - 理由：应尊重显式标题，而第一个 user 消息可以在不阻塞 LLM 提供商的情况下生成确定性的短标题。
   - 考虑过的替代方案：调用 LLM 进行标题生成。由于会引入延迟、外部故障模式和测试脆弱性，因此此次更改中被拒绝。

4. 以会话加有序消息数组的形式返回会话详细信息。
   - 理由：前端需要一个端点来渲染历史记录；列表保持轻量级并反向更新以提高可读性。
   - 考虑过的替代方案：让前端为每个会话手动连接列表和消息API。被拒绝，因为这会增加更多的往返请求和更多的状态耦合。

## Risks / Trade-offs

- 删除会话会永久删除消息历史记录。 → 保持删除 API 明确，并返回已删除的会话 ID，以便客户端可以确定性地更新状态。
- 元数据是灵活的 JSON 而不是规范化的引用/工具表。 → 定义稳定的契约键和测试，以便未来的规范化可以从已知的结构进行迁移。
- 标题生成是启发式的而不是由模型生成的。 → 保持生成的标题为确定性和有限的；未来的 LLM 标题生成可以更新同一个 `title` 字段。
- 会话列表尚未分页。 → 保持仓库排序的确定性，并将分页作为后续扩展功能，当列表大小需要时再实现。
