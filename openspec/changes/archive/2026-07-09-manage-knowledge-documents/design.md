## 上下文

后端已经具有经过身份验证的 FastAPI 路由、统一的响应帮助器、SQLite/Alembic 内存持久化、tenant 作用域的仓库模式、共享的 TypeScript API 合同，以及用于 chunk 插入/搜索的 Milvus 向量存储抽象。知识库文档仍然仅通过占位符摄入路由表示，因此没有持久化的文档元数据、没有明确的上传策略、没有文档列表/详细信息/删除 API，也没有 user 选择上传的前端工作流程。

当前的 tenant 模型使用经过身份验证的 user ID 作为 owner 和 tenant 范围。此设计保持该边界，并将每个 user 的默认知识库视为 `kb_<user id>`，直到引入单独的知识库域模型为止。

## Goals / Non-Goals

**目标：**
- 添加一个基于仓库的文档元数据模型，包含 owner 范围、知识库 ID、文件元数据、内容哈希、文档状态、索引状态和时间戳。
- 添加受保护的文档上传、列表、详情和删除路由，返回统一的响应包装器，并强制执行当前的 user owner 专属权限。
- 在共享的 API 合同中定义上传策略：允许的 MIME 类型/扩展名、最大大小、重复哈希行为以及显式的覆盖语义。
- 确保文档删除还会请求删除当前 tenant/knowledge-base 范围内该文档的 Milvus chunks。
- 为 user-initiated 上传、状态查看和删除添加一个前端身份验证的文档管理界面。

**非目标：**
- 完整文本提取，chunking，嵌入生成，异步索引工作者，或文档内容预览。
- 多个tenant组织或共享知识库。
- 启动时内置文档的摄入。
- 原始文件字节的对象存储。此更改存储元数据和足够的上传事实以驱动索引；字节可以在仓库边界之后添加。

## 决策

1. 在新的文档仓库协议背后的现有内存数据库中持久化元数据。
   - 理由：现有的 chat/AIOps/auth 数据已经使用 SQLAlchemy/Alembic 加上仓库合约。扩展该捆绑包可以保持与 PostgreSQL 的替换可行性，并避免 API 代码依赖 ORM 模型。
   - 考虑过的替代方案：一个单独的文档数据库模块。这将重复迁移/session 的 plumbing 工作，而目前没有明确的优势。

2. 使用 `owner_user_id` 作为 tenant 范围和默认知识库 ID `kb_<user id>`。
   - 理由：这与当前的授权规范和现有的 `/knowledge-bases` 路由相匹配。同时，在存在命名的 user 创建的知识库之前，它保持前端选择的简单性。
   - 考虑的替代方案：现在引入一个知识库表格。这在以后很有用，但对当前的文档管理界面来说是不必要的。

3. 以 `multipart/form-data` 接受上传，并可选地包含 `overwrite` 表单字段。
   - 理由：浏览器文件上传本质上是多部分的。API 可在服务器端计算文件大小/哈希，并在保留元数据之前拒绝不支持的文件。
   - 重复行为：如果相同的owner、知识库和内容哈希已经存在，除非`overwrite=true`，否则上传将返回`BUSINESS_CONFLICT`。使用覆盖时，该哈希的现有文档记录会被标记为已删除，其向量会被删除，并创建一个新的文档记录。

4. 将上传策略作为代码级常量存储，并通过合约导出，在 OpenAPI 中记录。
   - 理由：前端和后端必须就最大大小、MIME/扩展名白名单以及覆盖语义达成一致。将这些值保留在 `packages/api-contracts` 中可以让测试捕获偏差。

5. 将 `delete_document_chunks(...)` 添加到 Milvus 向量存储抽象中。
   - 理由：文档删除不应留下可检索的 chunk。使用 tenant、知识库和文档 ID 的文档范围 Milvus 删除过滤器提供了一个小而可测试的边界，可以被未来的索引作业重复使用。

## Risks / Trade-offs

- [风险] 在处理请求时如果完全读取大型多部分上传，可能会消耗内存。 -> 缓解措施：在持久化之前强制设置一个保守的最大大小，并保持对过大请求拒绝的测试。
- [风险] 删除向量可能在元数据删除后失败。 -> 缓解措施：在 API 流程中标记文档为已删除之前执行向量清理；如果清理失败，返回系统错误。
- [风险] 上传目前仅存储元数据，因此索引无法以后重放字节。 -> 缓解措施：将原始字节持久化排除在范围之外，但保留内容哈希、文件名、大小、MIME 类型、来源和状态字段，以便添加存储后端而不更改公共 API。
- [风险] 默认知识库 ID 是派生的而不是持久化的。 -> 缓解措施：仓库 API 仍然接受 `knowledge_base_id`，为真正的知识库仓库留出空间。

## 迁移计划

添加一个 Alembic 迁移，创建 `knowledge_documents` 并带有 owner/knowledge-base/hash/status 索引。现有部署可以升级到最新版本。回滚会删除文档表和索引；不需要遗留数据迁移，因为之前不存在文档表。

## 开放问题

此更改无需内容。文件解析、对象存储和异步索引有意推迟到后续更改中。
